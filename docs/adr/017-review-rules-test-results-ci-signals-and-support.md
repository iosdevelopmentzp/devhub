# ADR 017. Review rules, test results, CI signals and the support bundle

Date: 2026-11-07. Status: in progress (see the step log).

## Context

After ADR 015 the owner picked the next batch from a list of ideas (2026-11-07):

1. A custom rule for which requests count as "not reviewed by me". On one project every open request counts; on another only the requests assigned to the owner or to a GitHub team the owner is in, while that team has not approved.
2. A reminder when a request waits for the owner's review for too long. The Today card counts, nothing nudges.
3. The known gaps of the Pull Requests tab from `docs/STATUS.md`: the people list reads one page, teams are not offered as reviewers, Explain cuts a diff over 60,000 characters, "Changed since your review" does not see a review made in the browser.
4. Test results from the `.xcresult` bundle in the Test runs panel: the failed tests with their message and file, the slowest tests, the attachments (snapshot images) and a re-run of the failed tests only.
5. Flaky tests that DevHub finds itself from its CI history, because CircleCI Insights has no flaky list for a GitLab project or a GitHub App project (ADR 015, open question).
6. A dot on the menu bar icon when the CI of an own request failed or a job of it waits for an approval.
7. A support bundle for a bug report: everything in one redacted text, with as few links, project names and other private facts as possible.
8. A crash of DevHub itself shown at the next launch, with a copy for a bug report.
9. Run & Attach on a physical device (ADR 008, step 7b, only this part).

## Findings (2026-11-07)

- `gh auth login` gives the scopes `repo`, `read:org`, `gist` and `workflow`; `read:org` is enough for `gh api user/teams --paginate` (the teams of the user, with `slug` and `organization.login`) and for `repos/<owner>/<repo>/teams --paginate` (the teams with access to the repository). The GraphQL field `reviewRequests { nodes { requestedReviewer { ... on User { login } ... on Team { slug } } } }` names the teams asked for a review; GitHub removes a team from the review requests when a member of the team reviews, so a team still in the list has not reviewed. `gh pr edit --add-reviewer <org>/<slug>` asks a team. `reviews(author: <login>, last: 1) { nodes { submittedAt state } }` gives the last review of one user. GitLab has no teams and no review objects; the "assigned" rule works there with reviewers and assignees only.
- `xcrun xcresulttool get test-results tests --path <bundle>` (schema version 0.1.0 on this Mac): `testNodes[]` is a tree of `nodeType` (`Test Plan`, `Unit test bundle`, `UI test bundle`, `Test Suite`, `Test Case`, `Test Case Run`, `Repetition`, `Failure Message`, `Source Code Reference`, `Attachment`, …) with `name`, `nodeIdentifier`, `nodeIdentifierURL`, `result` (`Passed`, `Failed`, `Skipped`, `Expected Failure`, `unknown`), `duration` (text) and `durationInSeconds`, `details`, `children`. A `Failure Message` child carries the message in `name`; a `Source Code Reference` child carries `file:line` in `name`. `xcrun xcresulttool export attachments --path <bundle> --output-path <dir> [--only-failures] [--test-id <id>]` writes the files and prints a JSON array of `testIdentifier`, `attachments[]` with `exportedFileName`, `suggestedHumanReadableName`, `isAssociatedWithFailure`, `timestamp`. `xcodebuild test -only-testing:<target>/<class>/<test>` runs one test; the identifier of a test node is `<target>/<class>/<test>()`.
- `xcrun devicectl device process launch --start-stopped --json-output <file>` launches an app on a device suspended, so a debugger can attach before the first line runs. The Xcode attach of DevHub selects a run destination by `device identifier`; a physical device shows there with its UDID, which `DevicectlListParser` already uses as the id (`hardwareProperties.udid`). `ps` cannot tell whether a process on a device is stopped.
- macOS writes a crash of DevHub to `~/Library/Logs/DiagnosticReports/DevHub-<date>.ips` with `bug_type` 309, the same format `IPSCrashReportParser` reads for the simulator apps. `FileCrashReportRepository` keeps only reports with a simulator id.
- `CIWorkflow.runID` is the pipeline of the workflow; two workflows with the same run id ran the same commit, so a test that failed in one and passed in a later one of the same run flaked.

## Decisions

1. **Review queue rule.** `git.pullRequests.reviewQueue` in `project.json`: `"open"` (the default, today's rule: open, not a draft, not mine, not approved by me) or `"assigned"` (open, not a draft, not mine, not approved by me, and I am a requested reviewer or an assignee, or a team I am in is still a requested team). `PullRequestSummary` gets `requestedTeams: [String]` (team slugs, GitHub only). `CodeHostRepository` gets `myTeams(repository:) -> [String]` (GitHub: `user/teams`, the slugs of the organisation of the repository; GitLab: empty). `ReviewQueuePolicy.needsMyReview(request, username:, teams:, rule:)` decides; `OpenPullRequestsStore` reads the teams once per project (a failure is logged once and means no teams) and passes them with the rule to the policy, the row mapper and the Today card. The example config and `docs/extensions.md` show the key.
2. **Review reminder.** `OpenPullRequestsStore` remembers when a request entered my review queue (`gitlab.reviewSince.<project>`: number and date) and reminds once per request when it stayed there for `reviewReminderHours` (an app setting in Settings → Notifications, default 4, 0 is off): the notification kind `reviewReminders` ("Reviews waiting for me for too long"), the title "#12 waits for your review for 5 h", the target the request. A request that leaves the queue forgets its date; a request that enters it again gets a new reminder. `ReviewReminderPolicy` (Domain) picks the due requests.
3. **People and teams.** `people(repository:)` reads every page (`--paginate`) on both hosts. `CodeHostRepository` gets `teams(repository:) -> [String]` (GitHub: the teams with access to the repository as `<org>/<slug>`; GitLab: empty). The reviewer menu lists the people, a divider, then the teams; a team checks when its slug is in `requestedTeams`; `updatePeople` passes `<org>/<slug>` to `gh pr edit --add-reviewer`. `PullRequestPeopleStore` keeps the teams next to the people.
4. **Reviews made in the browser.** `PullRequestDetails` gets `myLastReview: (date, state)?` and `commitDates: [Date]` from GraphQL (`reviews(author: viewer)`, `commits(last: 50)`). `ReviewChangePolicy.commitsSince(review, commitDates:)` counts the commits after that review. When there is no local snapshot, or the host review is newer than it, the details chip says "N commits since your review on GitHub, 2 h ago" with a hint, and the file marks stay off; with no commit after the host review, DevHub stores the current fingerprints as the review snapshot with that date, so the marks work from then on. GitLab: no change.
5. **Explain in parts.** `AITextPromptBuilder.explainParts(...)` splits the files into parts of at most `patchLimit` characters each (a single file over the limit is cut as before), at most 5 parts; `AITextStore.explain` runs the parts one after another with the same provider and joins the answers under "Part N of M" headers; the card says "Reading part 2 of 3…" while it runs; the files left out after the fifth part are named at the end.
6. **Test results from the bundle.** `TestRunRepository` gets `results(bundlePath:) -> TestResultBundle` and `exportAttachments(bundlePath:folder:) -> [TestAttachment]`; `XcresultParser` (Data) flattens the tree into `TestResultCase` (identifier, target, class, name, result, duration, failure message, file, line) and `XcresultAttachmentParser` reads the export JSON. After a run `TestRunsStore` reads the bundle: the panel lists the failed tests with their message, file and line (a click opens the file in Xcode with `xed -l`), a folded "Slowest tests" list (10), and, per failed test, its attachments as images with the name (snapshot tests attach the reference, the failure and the diff); the files go to `~/Library/Application Support/DevHub Generic/Attachments/<bundle name>/` and are removed with the bundle. "Run failed again" runs `xcodebuild test` with one `-only-testing:` per failed test (`TestRunRequest.onlyTests`). The text output stays the live source while the run goes; the bundle is the source after it ends.
7. **Own flaky tests.** `FlakyTestLedger` (Presentation, next to `CIWorkflowHistory`) keeps `gitlab.flakyTests.<project>`: per test (class and name) the times it flaked and the last date. `CIWorkflowHistory.remember` calls `FlakyTrackingPolicy.flakes(new:earlier:)` with the earlier records of the same request and the same `runID`: a test in the failed list of an earlier record that is not in the failed list of the new record while the new workflow passed, or while its job passed, flaked once. `CIFlakyTest` gets `source` (`insights` or `devhub`). The detail store, the auto re-run store and the failed-test rows use the merged list (Insights and the ledger; the higher count wins); the tag says "flaky · flaked 2 times (DevHub)". "Forget" of a request's history leaves the ledger alone; Settings → the requests section gets "Forget flaky tests".
8. **The menu bar dot.** `StatusItemState` gets `ciFailed` (red dot) and `ciWaiting` (orange dot) between `failed` and `awake`: an own open request whose checks failed (`OpenPullRequestsStore`), or a job on hold (`CIWatchStore.onHold`). The dot stays while the fact lasts. The app setting `showCIStateInMenuBar` (default on) turns it off; the hint of the icon names the request.
9. **A crash of DevHub.** `CrashReportRepository` gets `ownReports(processName:since:)` (the same folder, `bug_type` 309, the process name, no simulator). `AppCrashStore` (Presentation, Features/Settings) reads at launch the reports newer than `app.crashSeenAt`; the newest shows as a `NoticeBar` over the Home tab ("DevHub crashed 10 min ago: EXC_BAD_ACCESS in …", "Copy for a bug report", "Dismiss") and as a failure line in Recent; "Copy" puts the redacted report on the pasteboard (decision 10). Dismiss saves the date.
10. **Support bundle.** `SupportBundleStore` and `SupportBundleBuilder` (Presentation, Features/Settings) extend the CI diagnostics into one text: DevHub (version, commit, macOS, Xcode), the settings without paths (window mode, editor, terminal, notification switches), the project (kind, `<scheme>`, `<bundle>`, the config problems), the Doctor tools, the last 100 commands of every tool with the head and the tail of their output, the last 50 lines of Recent, the CI section of ADR 015, the last crash of DevHub. `CIRedactionPolicy` becomes `RedactionPolicy` with more rules: every URL becomes `<url>`, every e-mail `<email>`, every IPv4 address `<ip>`, a token (`ghp_…`, `gho_…`, `github_pat_…`, `glpat-…`, 40 hex characters) `<secret>`, the macOS user name `<user>`, the project folder `<project>` and the project name, the scheme and the bundle id `<project>`, `<scheme>` and `<bundle>`; then the subjects and the denylist as before. "Support Bundle…" (save) and "Copy Support Bundle" in Settings → Doctor; the CI items of the checks header stay and use the same policy.
11. **Run & Attach on a device.** `XcodeAttaching.attach(pid:destination:projectPath:container:)` takes `AttachDestination.simulator(udid)` or `.device(udid)`; the attacher selects the run destination by the same `device identifier` script, and for a device waits 5 seconds after "Attach" instead of polling `ps`. `LaunchInstalledAppUseCase.executeOnDevice` launches with `--start-stopped` when `attachDebugger` is on, reads the pid from the JSON output and calls the attacher. The row enables Run & Attach for a connected device with the app installed. This closes the Run & Attach part of ADR 008 step 7b.

## Verification on a live project

GitHub: a request where a team of the owner is a requested reviewer must show in the "To review" scope with the `assigned` rule and leave it after a team member reviews; "Teams" in the reviewer menu adds a team; a review submitted in the browser must show as "N commits since your review on GitHub". Tests: a run with one failing snapshot test must show the message, the file and the images; "Run failed again" must run only that test. Device: Run & Attach on a connected iPhone must stop in Xcode at the first line. The flaky ledger needs two runs of the same commit with a test that failed and then passed. Every command must appear in the Output panel.

## Open questions

- Whether Xcode's "Attach to Process by PID or Name…" takes the pid of a device process when the run destination is that device, or needs the process name. The name of the executable is the fallback (`CFBundleExecutable` of the local build).
- Whether `xcresulttool export attachments` keeps the order of the reference, failure and diff images of a snapshot test; the names of swift-snapshot-testing attachments carry the role.
- The review queue of GitLab: the "assigned" rule has no teams there; an approval rule with a group is not read.
