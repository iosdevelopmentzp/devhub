Last updated: 2026-11-08 (ADR 017: review rules, test results, CI signals and the support bundle)

## Decisions

Numbered. What, then why. A later session must not undo these without a new numbered entry that explains the change.

1. The remote `origin` is a public GitHub repository, and `main` is pushed after green commits. Never force-push. Why: the owner decided so on 2026-10-30, to use the app on another Mac. The code was never pushed before that date. Everything pushed is public, so the anonymity check runs before every push. A separate playground repository tests the pull request features.
2. Own `NSStatusItem` and `NSPanel`, not `MenuBarExtra`. No sandbox, ad-hoc signing, `LSUIElement`. Why: shell commands need it, and the panel needs its own position, size and close rules. Changed by ADR 005 (2026-10-27): a second mode, "Normal window" (Settings → General → Window), gives one main window with a Dock icon and a main menu. The panel stays the default, so `LSUIElement` stays `YES` and window mode sets the activation policy to `regular` at start. `AppContainer` is the app delegate, for the Dock click.
3. Config over code: no project name, path, bundle ID, host or branch name in Swift. `Scripts/check-anonymous.sh` enforces the names; `.claude/rules/anonymity.md` lists the sample vocabulary.
4. The owner's own words live in `~/.devhub/anonymity-denylist.txt`, outside the repository. Why: the list itself would name the projects.
5. The package architecture of the main DevHub is the base: modules `Domain`, `Data`, `Mocks`, `UI`, `Presentation`, `Composition`, `TestSupport`, Swift 6, Swift Testing with spies. `docs/ARCHITECTURE.md` is the contract.
6. Common branch names (`main`, `master`, `develop`, `dev`) are not project names and may appear in tests and defaults. The remote comes from `git.remote` (`GitSettingsPolicy.defaultRemote` is `origin`), and every git command, `BranchName` and policy takes the remote name as a parameter.
7. The first launch has no project. `ProjectSession.selectedProject` falls back to `Project.none` and `RootView` shows `NoProjectState` instead of a tab. Why: the main app had a fixed default project, and a generic app cannot know one.
8. The Network tab lists only the exchanges of the DevHub mock server. Why: the session log was the log format of one app. `NetworkStore` keeps selection, filter, pause and clear over the server exchanges.
9. Debug launch switches live in `DevHubComposition/Debug/DebugLaunch.swift` and are compiled in Debug builds only. Today: `DEVHUB_PROJECT`, `DEVHUB_OPEN_PANEL`, `DEVHUB_TAB`, `DEVHUB_SNAPSHOT`, `DEVHUB_SNAPSHOT_DELAY`, `DEVHUB_RUN_ACTION` (comma-separated action ids, run with default inputs), `DEVHUB_REQUEST_ACTION` (one id, opens its prompt), `DEVHUB_SHOW_OUTPUT`, `DEVHUB_GIT_OPS` (comma-separated steps such as `fetch,stage:a.txt,commit:Message,push,wt-create:feature/x,switch:topic,delete-branch:topic`; each step waits until the stores are idle; the list is in `PresentationAssembly+DebugGitOps.swift`). `DEVHUB_PROJECT`, `DEVHUB_TAB` and `DEVHUB_SHOW_OUTPUT` change saved preferences. Later switches: `DEVHUB_WINDOW_MODE` (`panel` or `window`, saved), `DEVHUB_PULL_REQUEST` (a number: opens that request in the Pull Requests tab), `DEVHUB_BUILD_RUN` (with `DEVHUB_BUILD_PROFILE`, `DEVHUB_BUILD_BRANCH`, `DEVHUB_LAUNCH_ID`), `DEVHUB_MOCK`, `DEVHUB_LOG_STREAMS`, `DEVHUB_PALETTE`, `DEVHUB_PULL_REQUEST_WINDOW=1` (opens the request of `DEVHUB_PULL_REQUEST` in its window; the snapshot draws that window), `DEVHUB_REVEAL_FILE=<path>` (scrolls the details to that file), `DEVHUB_DIFF_LAYOUT=unified|sideBySide`.
10. Snapshot trap: SwiftUI does not redraw a panel that is covered by other windows, and `cacheDisplay` does not draw some controls (a prominent button looks empty). Check results on the command line as well as in the picture.
11. The scripts stop only the build of this repository, by its executable path. Why: another app with the same name (`DevHub`) can run on the same machine.
12. The app keeps the bundle ID `devteams.DevHub` of the first generic app, so it reads and writes the same preferences domain.
13. "Copy for Slack" is "Copy Link with Title" (`RequestLinkText`): the reference, the title and the link.
14. `waitUntil` waits 10 s by default, not 2 s. Why: right after a build, about 25 store tests timed out on the busy main actor while the same tests passed alone. The wait is the main-actor queue of a parallel run, not CPU load (decision 47).
15. The `.devhub/` config models are `Codable` Domain types (`Models/Config/`), the one exception to "no `Decodable` Domain model" (`docs/ARCHITECTURE.md` section 5). `ExampleConfig.files` is generated from `docs/examples/devhub/` by `Scripts/generate-example-config.sh`; run it after every change there.
16. After a change to an enum in a lower module (for example a new `Tint` case), remove `Packages/DevHubKit/.build` before `Scripts/test.sh`. Why: the incremental test build once kept old object files, and the tests read wrong enum values.
17. A config action in a row placement shows its inputs and confirmation under that row. The screen draws the prompt (`ConfigActionsStore.pending(in:)` with the slot `<placement>:<row id>`), the row gets only `configActions` in its model and an `onConfigAction` closure. Why: a row reads no store but `Toaster` and `AppActions`.
18. A remote whose host name contains neither `github` nor `gitlab` counts as GitLab unless `git.host.kind` says `github`. Why: a self-hosted GitLab on a company domain is the common case; GitHub Enterprise users set the kind once. The ADR idea to ask `gh auth status` was dropped: it would make the choice depend on the machine.
19. The code host types use pull request words: `PullRequestSummary`, `CodeHostRepository`, `PullRequestsStore`, `ReviewThread`, `MergeReadiness`, `CheckStatus`, the tab id `pullRequests`. The fields keep their names (`iid`, `pipeline`, `detailedStatus`), and the GitLab GraphQL strings keep the GitLab names (`MergeRequestState`, `mergeRequests`). Why: a field rename touches every mapper and test for no change in behaviour, and the GraphQL names belong to GitLab.
20. `.gitignore` ignores only the top-level `/build/` folder. Why: on the case-insensitive macOS file system `build/` also matched every `Build/` source folder, and the Build feature was missing from the commits.
21. UI words for the code host come from `CodeHostWords` (`Shared/`): "Pull Requests" and `#12` for GitHub, "Merge Requests" and `!12` for GitLab, "checks" or "pipeline". Mappers take `words:`; views and rows read `@Environment(\.codeHostWords)`, which `CodeHostRemote` sets after the first read of the remote. Before that the words are neutral ("Pull Requests", "Open in Browser"). Why: one place for the vocabulary, and rows need no new store.
22. Actions that a host or a repository does not allow are hidden, not shown with an error: `PullRequestPermissions.canRevokeApproval` (GitHub: write access) and `canSetAutoMerge` (GitHub: write access and `autoMergeAllowed` on the repository).
23. A `kind: command` project runs `build.command`, then `run.command`, in the checkout of the run bar, with the action variables (`DEVHUB_SIMULATOR_UDID`, `DEVHUB_BRANCH`, …). Both commands may print `@devhub {"app": "<path>"}`; a relative path is read from the checkout. A script file without the executable bit runs through `/bin/zsh`. Run & Attach stays off for these projects. Why: the app path is known only after the build, and a fresh clone often loses the executable bit.
24. Deep link schemes come from `CFBundleURLTypes` in the `Info.plist` of the app installed on the simulator, not from a `simulators.deepLinks` config key (ADR 001 section 7.5). Why: the app already declares its schemes, and a new key would change the config schema.
25. The AI tab does not check that `copilot` or `claude` is installed before Resume. Why: Resume runs in the terminal with the PATH of the user; the app's own PATH misses folders such as `~/.local/bin`, so a check from the app would hide working sessions. Settings → Doctor shows missing tools.
26. The Copilot token comes from `gh auth token` first and from the `copilot-cli` keychain item second. The keychain read stops after 10 s and is not tried again until the app restarts. Why: macOS can ask the user to allow `/usr/bin/security` to read that item; a background refresh every 5 minutes must not keep that dialog open or show it again and again.
27. The M6 config keys follow ADR 001 Appendix A, approved by the owner on 2026-10-18: `launch.identity.*`, `launch.profiles[].storage`, `upstream` and `production`, `network.baseURLVariable` and `network.mocksFolder`, and the `state` directive of the status script.
28. A launch identity is a plan, not stored state: `LaunchPlan` joins the profile, `launch.identity` and the chosen ID, and every launch (Build & Run, Launch, Apply & Relaunch) goes through `simulators.launch` with its environment and arguments. The result is a `LaunchRecord` (bundle ID, profile, ID, mock server URL) that `IdentityStore` saves per simulator under `simulators.launchSettings`. The old key `simulators.identity` is not migrated. Why: the old settings held an environment name and a hard-coded device ID format that no longer exist; a reset costs one choice per simulator.
29. The clean install rule (`CleanInstallPolicy`): with a chosen ID, reinstall when the actual ID (the `state` report, else the last ID DevHub set) differs. With no chosen ID, reinstall only when the actual ID is one that DevHub set or saved. With a chosen ID and no known actual ID (no `state` report and no earlier launch from DevHub), the first launch reinstalls once. Why: the app's own ID must not cause a reinstall on every Build & Run; that would lose the session each time.
30. The bundle ID of the identity panel and the mock server is the one of the last launch on that simulator when the project config knows it, else the effective bundle ID of the project. Why: `IdentityStore` sits below `BuildStore` and cannot read the run bar scheme; the last launch records what Build & Run really installed.
31. A custom tab has no store of its own: `CustomTabMapper` turns the tab config into sections, and the rows run through `ConfigActionsStore` like the scripts on Home. A source script is the header script action `script:<file name>`, so its run, result and last run time are shared with Home. Why: one place runs config scripts and keeps their results; a second store would copy that state.
32. Notifications for Build & Run and review requests go out only while the panel and the pinned window are both closed (`Notifier.postWhenClosed`). A `notify` directive of a script posts always, because the script asked for it. The permission is asked only from Settings → Notifications, never at app start. Why: an open panel already shows the result, and a permission dialog at start interrupts the user before DevHub did anything useful.
33. `PathToolLocator` looks in `/opt/homebrew/bin`, `/usr/local/bin` and `~/.local/bin` before the `PATH` of the app. Why: an app started from Finder or at login gets a short `PATH` without these folders, and Doctor would call installed tools "missing".
34. A GraphQL response with an `errors` array counts as failed in the Network tab, even with HTTP status 200. A mock rule matches a GraphQL operation by `operationName` with `*` as a wildcard; a batch matches when one of its operations matches. Why: GraphQL servers answer 200 for most errors, so the status code alone hides them.
35. ⌘1 to ⌘9 follow the positions in the tab bar. A custom tab starts in Utils (decision 71), so the built-in numbers stay the same in every project unless the user moves a tab. Tabs after the ninth and the sub-tabs of Utils have no shortcut.
36. The mock server of a simulator first tries a stable port from a hash of the simulator UDID (`MockServerPortPolicy`, 49152 to 59151) and takes any free port when that one is busy. Why: the app keeps the same base URL across DevHub restarts, so a relaunch is needed less often.
37. Two window modes: "Menu bar panel" (the default) and "Normal window" (ADR 005). `LSUIElement` stays `YES`; window mode sets the activation policy to `regular` at start, and `AppContainer` is the app delegate for the Dock click. Why: the main DevHub moved to a window app, but a generic app should keep the menu bar panel for users who want it.
38. `PullRequestPermissions.canRequestChanges` is true only on GitHub for a request by someone else. GitLab has no "request changes" review in `glab`, so the button is hidden there, not shown with an error (decision 22).
39. Simulator QA settings go through the typed `SimulatorSettingsRepository` port, and the language change waits for a reboot instead of rebooting the simulator. Why: a reboot closes the app under test without asking.
40. A job log in pull request details is cut to its last 200 lines in Data (`JobLogTail`), with timestamps, colour codes and tokens removed. Why: GitHub and GitLab logs can be many megabytes, and the end of the log holds the failure.
41. `Scripts/install.sh` installs to `/Applications/DevHub Generic.app`, not `/Applications/DevHub.app`. Why: the main DevHub lives at `/Applications/DevHub.app` and updates itself from its own repository; both apps must run on one Mac. The bundle IDs differ, so settings stay apart. Both apps can use the same global shortcut only if one of them changes it in Settings.
42. The pull request details hide nothing by default. A file is hidden when the user hid it (the eye-slash button or "Hide Them" on the suggestion line; `PullRequestHiddenFiles`, saved per project as paths) or when it matches `git.pullRequests.hiddenFiles` in `project.json`, matched by `fnmatch` against the full path and the file name (`HiddenFilePolicy`). The old built-in list (tests, Xcode project files, lock files) is now `HiddenFilePolicy.suggestedPatterns` and only feeds the suggestion. "Show N hidden" is per request and lives in memory (`PullRequestDetailStore.shownHiddenFiles`). Why: the owner wants to choose what to hide; a default that hid files silently was a surprise (changed on 2026-10-31). GitLab has no `approvalsRequired` or `approvalState` field on the owner's server, so the review block names people and never counts approvals.
43. Changes of your own open requests (approval, request for changes, failed checks, new comments, merged, closed) come from a comparison of two reads of the open list (`OwnRequestChangePolicy` in `OpenPullRequestsStore`), not from a new poll. A request that left the list gets one `status` read of its branch to tell a merge from a close. A refresh caused by your own action (`.pullRequestsChanged`) updates the baseline without a report. Why: the open list is read every 5 minutes in any case, and a report after your own comment or approval would name your own action.
44. "Build" (⌘B) is the Build & Run pipeline with `BuildRequest.launchesApp == false`: it stops after "Locate the app", and a `kind: command` project runs `build.command` only. `builtin.build` is not in the default Home grid (like `builtin.pullRequests`). Why: one pipeline, one store, one log; the grid stays at eight tiles.

45. Notification kinds are stored as the muted set (`AppSettings.mutedNotifications`), so a new kind is on by default and an old settings file keeps every kind on. The events of the app (`ActivityLog`) carry a kind and a place (`ActivityTarget`) and are saved for 30 days (`ActivityRetentionPolicy`, 500 at most) under `app.recentEvents`; the same event feeds the macOS notification, the Notifications screen and Recent on Home. Why: one list to look at, one place to mute a kind, and a click that leads somewhere.

46. CI runs on a GitHub-hosted `macos-26` runner (`.github/workflows/ci.yml`): layer check, anonymity check with the built-in patterns only, Debug build, smoke check, every test in a serial run. Why: two process hangs in `ShellRunner` and a test race were found by hand in parallel sessions; a run on a clean machine catches them before a push lands on `main`. The denylist is private, so CI cannot check the owner words.
47. CI runs the tests serially (`Scripts/test.sh --no-parallel`). Why: `swift test` queues every test at once, and in a parallel run every hop to the main actor waits for the queued main-actor tests: about 3 s on 14 cores, about 10 s on the 3-core runner, which is the `waitUntil` timeout, so the store tests timed out in every second CI run. A serial run has no queue. A local run stays parallel: 3 s is far from the timeout and the run takes 4 s instead of 17 s.
48. CircleCI through one Domain port (`CIRepository`) over the `circleci` CLI, on only when `CIPolicy.provider` finds `ci.kind: "circleci"` or `.circleci/config.yml` in the main checkout. Why: the GitHub checks stay the source of truth for the state (the link of a check carries the workflow UUID, `CIWorkflowLink`), and the tool adds the jobs, the logs, re-run, cancel, approve and the failed tests with the flaky label from CircleCI Insights. DevHub never calls the CircleCI web API itself and never holds the token (ADR 006). The fixtures follow the CLI reference; a live check is still open.
49. CircleCI history and auto re-run live in Presentation over the existing ports: `CIWorkflowHistory` saves finished workflows per project and request in the `KeyValueStore` (`CIHistoryPolicy`: 20 runs, 50 tests per job, 4000 characters per message); `CIAutoRerunStore` keeps one `CIAutoRerunPlan` per request, checks every minute from `AppWindows`, and decides with `CIAutoRerunPolicy` (re-run from failed while tries are left, wait 10 minutes for the new workflow of a re-run, stop on pass, cancel or the last try). `CIProjectResolver` holds the provider and slug rules that both stores use. Why: no new port is needed, the plan must survive a restart and run with the panel closed, and the detail store reads the history and the plan through `CIWorkflowHistory` and `CIAutoRerunLookup` instead of owning them.
50. **Operations (ADR 007).** Every action that a user starts is an operation. `OperationScope.current` (a Domain `@TaskLocal`) tags every command that `ShellRunner` starts inside it; `OperationLog` keeps the operations of the session in memory; the cards show in a tray at the bottom of the tab, over the list, one per operation, with the steps, the failure digest (`FailureDigestPolicy`) and Retry. The Output panel stays the full transcript and opens on a failure only with "Open When a Command Fails". Build & Run and the worktree test runs keep their own panels. A new place that runs commands for the user goes through `ActionRunner` or `OperationLog.start` so its card shows in the tray by itself, never a busy title alone.
51. **Xcode per project (ADR 007 D8).** `ShellRunner` holds one `DeveloperDirState`; `XcodeSelectionStore` sets it through `ToolEnvironmentRepository` when the project or its config changes (the choice in Settings → Projects, then `xcode.developerDir`, then nothing). Only `xcodebuild`, `xcrun` and `xed` get `DEVELOPER_DIR` (`DeveloperDirPolicy.tools`); `open -a` opens that Xcode. A port call never passes the folder by hand.
52. **Crash reports (ADR 007 D2).** `CrashReportsStore` starts watching on the first `appLaunched` event with a bundle ID and keeps one `FileCrashReportRepository.changes()` stream (a `DispatchSource` on `~/Library/Logs/DiagnosticReports`) until DevHub quits. No polling, no process. A report counts only when `CrashReportPolicy.matches` says so (crash type 309, simulator path, bundle ID, simulator, after the launch minus 5 s).
53. **App data (ADR 007 D3).** `SimctlAppDataRepository` reads and writes user defaults only through `simctl spawn <udid> defaults … <absolute plist path>`, never by editing the plist file: the simulator's `cfprefsd` caches the values, and a file edit would be lost or overwritten. The panel needs a booted simulator. Reset deletes the defaults domain first, then the files. `AppDataStore` drops the data when the panel closes.
54. **Changed since your review (ADR 007 D4).** `ReviewChangePolicy.fingerprint` is FNV-1a over the added and removed lines of a file diff (stable across launches, unlike `hashValue`); a binary or too large file uses its kind and line counts. `PullRequestDetailStore` computes the fingerprints once per load. `PullRequestReviewMemory` saves `ReviewSnapshot`s per project under `gitlab.reviews.<project>` (200 requests at most) and only while `AppSettings.remembersReviews` is on; turning it off removes every saved review. Approve reaches the detail store as `AppEvent.pullRequestReviewed`.
55. **AI text and Explain (ADR 007 D5).** One port, `AITextRepository.generate(prompt:command:cwd:)`, runs a one-shot command of Claude Code or Copilot CLI (`ai.textCommands`, defaults in `AITextCommandPolicy`) through `ShellRunner.stream` with `/bin/sh -c "exec …"`, so Stop cancels the task and the process ends with it. The prompt goes through a temporary file, never through the command line text, and the file is removed after the run. Prompts live in Domain (`AITextPromptBuilder`), so tests pin them; the diff is cut at 60,000 characters. `AITextStore` keeps one run per target (commit box of a checkout, new request of a branch, Explain of a request) and the explanations until the project changes; nothing is saved. The answer only fills a field: DevHub never commits or creates a request on its own.
56. **Disk cleanup (ADR 007 D7).** One port, `DiskCleanupRepository` (`items`, `size(of:)`, `clean`). `XcodeDiskCleanupRepository` lists the folders with `DiskFolderScanner` (file system only) and the simulators with `simctl list devices unavailable -j` and `simctl runtime list -j`; it measures with `du -sck` and deletes with `/bin/rm -rf --` through `ShellRunner`, so each delete is a command in the operation card and the Output panel. `DiskCleanupPolicy.isRemovable` is the only gate before `rm`: the path must be inside the DerivedData folder, `~/Library/Developer/Xcode` or `~/Library/Caches` (also after the symbolic links are resolved), never a root itself and never with `..`. `DiskCleanupStore` scans once per launch when Settings opens and measures four folders at a time; nothing is saved. The Disk section is one form row with its own dividers: with one form row per line, macOS drew the last line outside the section card.
57. **Simulator recording (ADR 008 D2).** `SimulatorSettingsRepository.record` runs `simctl io recordVideo` through `ShellRunner.stream(…, stop: .interrupt)` until its task is cancelled: the cancel sends SIGINT, and `simctl` writes the file and exits with 0. The recording is an operation of `SimulatorQAStore` with a stop closure. `AppContainer.applicationWillTerminate` calls `PresentationAssembly.prepareForQuit()`, which stops every recording; without it the `simctl` child would keep recording after DevHub quits.
58. **GIF and compressed video (ADR 008 D3).** One port, `MediaRepository`; `AVMediaRepository` in `DevHubData/Media/` is the only code that imports AVFoundation or ImageIO (`Scripts/check-layers.sh`). It runs in DevHub, without a process, so these conversions do not show in the Output panel. The repository chooses a free output path next to the source (`MediaOutputPolicy`) and returns it; Presentation never checks files. `MediaOutputPolicy.gifPlan` caps a GIF at 600 frames and never scales a video up. `MediaStore` runs each conversion as an operation with progress and a stop closure, one at a time per source file.
59. **Device frames (ADR 008 D4).** DevHub never ships frame images. `DeviceChromeLocator` reads the device type from `<device>/device.plist`, finds its `.simdevicetype` bundle by `CFBundleIdentifier`, takes `chromeIdentifier` and the screen size from `profile.plist`, then reads `chrome.json` and the PDF parts from `/Library/Developer/DeviceKit/Chrome`. `DeviceFrameRenderer` draws the `composite` image when the chrome names one, else the nine pieces, and clips every PDF part to its rectangle: the parts paint outside their media box. Buttons follow `anchor`, `align` and the `normal` offset (`DeviceFrameLayout`). A composite already has a black screen area; for the pieces DevHub fills the screen black, because the screenshot has transparent corners (`--mask=alpha`). `chrome.json` is not documented, so a fixture test pins the fields DevHub reads.
60. **Frames on GIF and video (ADR 008 D4).** One switch, `SimulatorQAStore.addsDeviceFrame` (key `simulatorQA.addsDeviceFrame`), frames screenshots and conversions; Convert passes the simulator to `MediaRepository` as `framedFor`, and the output name gets " framed". `DeviceFrameOverlay` draws the frame once per conversion: white outside the device, a hole in the screen whose corners are concentric with the outer outline of `chrome.json` (`paths.simpleOutsideBorder`). A full rectangular hole showed the corners of the video outside the round body. Each GIF frame is drawn under the overlay. An MP4 uses `FramedVideoComposition`: the video track scaled into the screen, the overlay above it through `AVVideoCompositionCoreAnimationTool` (the `Configuration` API of macOS 26), a render size with even numbers inside the long side of the preset (1280 or 1920) and never above the pixels of the device. Recordings use `--mask=black`, so the corners of the screen are black like the bezel. A simulator recording has a variable frame rate: `simctl` writes a frame only when the screen changes. `AVAssetImageGenerator.images(for:)` fails with "Cannot Decode" for every time after two times fall on the same frame, so `AVMediaRepository` first reads the sample times with `AVAssetReader` (no decoding), and `MediaOutputPolicy.gifFrames` asks for each frame once and merges repeats into one longer GIF frame. The GIF is built in memory and written in one step, so a failure or Stop leaves no partial file.
61. **Video compression uses ffmpeg (ADR 009).** `AVAssetExportSession` has fixed presets and no quality factor, so the Utils tab compresses with ffmpeg and x264 (CRF 20, 24 or 28 for High, Balanced and Small; long side up to the source, 1920 or 1280; up to 60, 30 or 30 fps through `-fpsmax`). `FFmpegVideoCompressionRepository` runs the tools by the path that `ToolLocating` finds, so `CommandKind.classify` sorts a full path by its last component. ffmpeg writes a hidden partial file next to the result and DevHub renames it at the end, so a failure or Stop leaves nothing. DevHub installs ffmpeg only with `brew install ffmpeg`; it never runs the Homebrew installer, which needs an administrator password.
62. **The Utils tab (ADR 009).** `FeatureID.utils` (⌘9) holds tools that do not belong to a project; `UtilityID` is the sub-tab, saved under `utils.selection`. Compress Video keeps its jobs in memory only (`VideoCompressionStore.jobs`); the quality and the sound switch are saved under `utils.video.settings` and copied into each job when it is added. One job runs at a time in its own task, so Stop cancels only that job and the queue goes on. Jobs added while ffmpeg is missing wait and start after the install. The result row drags the file through `NSItemProvider(contentsOf:)`, so a chat gets the MP4 itself. `WorkspaceActions.revealInFinder` selects a file in Finder; `openInFinder` opens a plain folder and selects a file or a package (`.app`), so "Show in Finder" never opens or runs the file.
63. **Drop on the menu bar icon (ADR 009 D6).** The panel closes on any click outside DevHub, so a file cannot be dragged from Finder into it. A `FileDropView` covers the status item button: it registers for file URLs and takes a drop of videos, which opens the panel or the window on Utils → Compress Video and starts them. The view also receives every click on the icon, so it passes left and right mouse down to `statusItemClicked` and answers `acceptsFirstMouse` with true. Checked with a synthetic mouse down sent to `NSStatusBarWindow`: the hit view is `FileDropView` and the panel opens.
64. **Worktrees inside the project follow the git ignore rules.** DevHub stores no setting for the place of new worktrees. `WorktreeRepository.location` returns `.configured` when `git.worktrees.folder` is set; otherwise `.insideProject` when `git check-ignore -q .worktrees/` says the folder is ignored (`.git/info/exclude` or `.gitignore`), else `.nextToProject`. `create` reads the location each time, so every caller (New…, Git, Pull Requests, the palette, a build from a branch) follows it. "Keep Inside the Project" appends `# Worktrees created by DevHub` and `.worktrees/` to the file that `git rev-parse --git-path info/exclude` names (the common git folder, also from a linked worktree), never twice, then checks again and fails when a negated `.gitignore` rule still shows the folder. `.git/info/exclude` is local and never committed, so the team is not affected. DevHub does not move existing worktrees and has no button to go back: remove the line from `.git/info/exclude`.
65. **Simulator.app or Device Hub (ADR 008 D1).** Xcode 27 has no Simulator.app, so DevHub never opens the simulator window by the app name alone. `SimulatorAppLocation.find` looks in the developer folder of the project (`ShellRunner.developerDir`, else `xcode-select -p`): `<developer dir>/Applications/Simulator.app` first, then `<Xcode>/Contents/Applications/DeviceHub.app`. Device Hub gets `simctl boot` before `devices://device/open?id=<udid>`, because it shows no window for a device that boots after the URL. Only when neither app is found does DevHub try `open -a Simulator`, then Device Hub by its bundle ID. The `devices://` URL is not documented by Apple; the React Native CLI and the Expo CLI use it.
66. **The search field in the tab (ADR 010 D1).** `TabSearchField` (`Shell/`) sits in the toolbar of each tab, next to the list it filters, not in the header. One text per tab in `ProjectSession`, ⌘F focuses it, Esc clears it. Why: the header was far from the list, and on Simulators the run bar stood between them.
67. **The operations tray (ADR 010 D2).** Operation cards show in `OperationsTray`, an overlay at the bottom of the tab over the list and above the Output panel, one card per operation that is not dismissed, newest at the bottom. Nothing is placed inline, so the content never jumps; several operations at once are several cards. A request window has a tray for its request. Why: inline cards pushed the content down when a command started.
68. **The checkout badge (ADR 010 D3).** The run bar and the Git header show the checkout as a badge from `CheckoutBadgeMapper`: gray "Main checkout · <branch>" for the main checkout, orange "Worktree · <name>" or "Branch · <name>" for anything else. A click opens the menu as before. Why: a build or a Git action in a worktree looked the same as one in the main checkout.
69. **Dependency and tool policy (ADR 011).** No library at all; a copy in `Packages/Vendor/` would be the first choice if one is ever needed. Any new package, executable, GitHub Action, host or version change needs the owner's consent after a risk analysis (`.claude/rules/dependencies.md`). `Scripts/check-dependencies.sh` enforces `Scripts/allowed-tools.txt` and `Scripts/allowed-hosts.txt` and a commit SHA on every Action; `docs/DEPENDENCIES.md` says what each tool sends where. `TelemetryOptOutPolicy` turns the telemetry of the tools off for every child process. "Show usage for: Off" stops the only network calls DevHub makes itself. Why: no data may leave the Mac for a service the owner did not choose.

70. **Shared tab inputs, `copy` runs and the Recent list live in `ConfigActionsStore`.** A tab's `inputs` are saved under `configActions.tabInputs` per project and tab and reach every run of the tab through `ActionItemContext.inputs`; `ActionContextPolicy` puts them under the action's own inputs. `ActionConfirmationPolicy` (Domain) picks the confirmation: the `confirm` of the chosen choice option, of the action or of the tab, else the action's `confirm`; an action without inputs opens a prompt when that gives a text. A `copy` run expands its template, copies, records a `ConfigCopyRecord` (`configActions.copyHistory`, 30 per project) and opens the target; the preview under the inputs uses the same context without the containers. Why: a chat command tab is config only (`docs/customization.md` §3); no feature-specific tab, and no second store for a custom tab (decision 31).

71. **Utils is the container of the extra tabs; the user moves tabs with a right-click.** `TabID` has three cases: `feature`, `utility` (`utility.<id>`) and `custom` (`tab.<id>`). `TabLayout` (Shell) gives every tab a `TabPlacement`: Home and Utils are fixed in the bar, a built-in tab starts in the bar, a tool and a custom tab start in Utils unless the tab file says `placement: bar`; the user's moves are saved under `tabs.layout` and win. `Navigator` owns the bar selection, the Utils sub-selection (`utils.selection`, the old plain `compressVideo` value still reads) and the layout; `show(_:)` routes a tab to the bar or into Utils, and `currentTab` is the tab on screen, which the search field and the saved search text follow. `UtilsStore` is gone. Why: the bar does not fit ten tabs at the minimum width, and a new `.devhub` tab must not push the built-in numbers; one place (`Navigator`) decides where a tab opens, so notifications, the palette and `DEVHUB_TAB` need no knowledge of the layout.


72. **Review file groups, diff marks, side by side, the window sidebar (ADR 012).** `git.pullRequests.fileGroups` names groups by patterns; `FileGroupPolicy` puts each file into the first group that matches, and a chip per matched group hides or shows it per request (`PullRequestDetailStore.toggledGroups`, in memory; `hidden: true` starts hidden). `DiffLineEmphasis` pairs the removed and added lines of a block and marks the tokens that differ (no marks under 40 % shared characters). `DiffLayout` is saved in `PullRequestsStore` (`gitlab.diffLayout`); `SplitDiffMapper` builds the side-by-side rows from the unified line models, and the picker is disabled under 600 points. The request window has `PullRequestFileSidebar`; `revealFile` expands a file and the file header scrolls itself into view from a `.task(id:)`. The file list is a plain `VStack`: a lazy stack never materialised a file below the fold, so a scroll to it did nothing. Why: hiding by groups is the daily case, the changed word is what a reviewer looks for, and the window has the room the panel does not.

73. **Stash contents and the branches of a commit (ADR 013).** `GitStash.hash` names the stash commit; `GitChangesRepository.stashFiles` and `stashDiff` read it with `git show` (the third parent for untracked files), and `CommitHistoryStore` keeps the expansion under `stash:<hash>` with `stashHashes` choosing the stash commands, so the stash row reuses the commit file list and diff views. `GitCommand.stashBranch` runs `git stash branch`. `branchesContaining` (`git branch -a --contains`) fills the "In …" line of an expanded commit, cached per hash until the branches change. Why: a stash was a black box, and the decorations of a commit say nothing about the branches that already have it.

74. **Self-update from the pushed `main` (ADR 014).** `install.sh` keeps a build clone under `~/Library/Application Support/DevHub Generic/source` and writes `update/installed.json`; `FileUpdateRepository` checks that commit against `origin/main` with `git merge-base --is-ancestor` and `git log` in the clone, and starts `Scripts/update.sh` detached. `UpdateStore` checks at launch and every 5 minutes, follows `status.json` every second, quits the app (`onInstalling`) when the phase is `installing`, and `UpdateLaunchPolicy` reads the status after launch (`done` with the installed commit shows the toast once; a running phase without a live pid is a failure). The git hooks and `auto-install.sh` are gone. Why: the hooks installed every local commit, a clone without them never updated, and an Apple event from the script would need an Automation permission.

75. **CI depth over the same port (ADR 015).** The job facts that `workflow get` lacks (durations, job numbers for links, approval request ids) come from API v2 through `circleci api api/v2/workflow/<uuid>` and `/job`; the steps from `job get`; the artifacts from `job artifact`. Three Presentation stores read through `CIRepository` and the lookups: `CIWatchStore` (approval jobs on hold of the own open requests, one notification per job, remembered per project), `CIBranchRunsStore` (the latest run of the current branch for the Git header, the base branch every 5 minutes) and `CIDiagnosticsStore` (the report text from the command log, the activity log and the parsed state, redacted by `RedactionPolicy` with the subjects of the remote and the words of `~/.devhub/anonymity-denylist.txt` through `RedactionWordsRepository`). `CIAutoRerunPlan.onlyFlaky` (default on) makes `CIAutoRerunPolicy` stop a plan with the reason from `CIFailurePolicy`. Why: the CLI reference and the source of the CLI give these shapes; a separate CI tab was not needed, the jobs of a branch run are one click away through the request; a shareable diagnostics file is the only way to debug a live project the owner cannot show.

76. **Jira through `jira-cli`, the token outside DevHub (ADR 016).** `IssueTrackerRepository` with `JiraIssueRepository` runs `jira` through `ShellRunner`; `toolState()` reads the path, the config file `~/.config/.jira/.config.yml` and `jira me`. The token lives in the keychain item `jira-cli`, in `~/.netrc` or in the shell, never in DevHub. `tracker.*` in `project.json` (`TrackerSettingsPolicy`); without `tracker.kind`, a Jira `git.ticketURL` turns the tab on. `TrackerQueryPolicy` builds the JQL of the two scopes and `--order-by updated` sorts; `TrackerBranchPolicy` builds `feature/{key}-{slug}`. The model is `TrackerIssue`, not `Issue`: Swift Testing has an `Issue` type. Why: the owner chose jira-cli over the closed Atlassian CLI (open source, Cloud and Server, `--raw` JSON, keychain token), and a tool with the user's login needs no host in `allowed-hosts.txt` and no login flow in DevHub.

77. **Review rules, test results, CI signals and the support bundle (ADR 017).** `ReviewQueuePolicy` decides the review queue from `git.pullRequests.reviewQueue` and `ReviewerIdentity` (my login and my teams from `myTeams(repository:)`); the store, the Today card, the badge and the reminder use the same rule. `ReviewReminderPolicy` reminds once per request after `reviewReminderHours`. The people and team lists read every page (`JSONPages.split` over `gh api --paginate --slurp` and `glab api --paginate`). The test panel takes its facts from the `.xcresult` bundle after a run (`XcresultParser`, `XcresultAttachmentParser`); the text output stays the source while the run goes. `FlakyTrackingPolicy` counts a test as flaky when it failed and then passed in workflows of the same pipeline; `FlakyTestLedger` keeps the counts per project and merges them with the Insights list. `StatusItemState.ciFailed` and `.ciWaiting` draw a red or orange dot. `RedactionPolicy` (renamed from `CIRedactionPolicy`) cleans the support bundle and the crash text: secrets, links, e-mails and IP addresses first, then the project folder, home, user, bundle, scheme and project names, then the denylist subjects. Run & Attach on a device launches with `devicectl --start-stopped` and attaches by the process ID. Why: the owner's projects count "not reviewed" differently, CircleCI Insights has no flaky list for GitLab or GitHub App projects, and a bug report must not leak project names or links.

- Test results from the `.xcresult` bundle: the parser and `-only-testing` were checked on a real bundle of a scratch package (`xcresulttool` schema 0.1.0). The reference, failure and diff images of a real snapshot test were not seen; whether `xcresulttool export attachments` keeps their order is an open question in ADR 017.
- Own flaky tracking: checked by tests over the mock ports. It needs two workflows of the same pipeline in the saved history, so a request with one run finds nothing.
- Menu bar dot, support bundle and the notice for a crash of DevHub: checked by tests and a headless snapshot of Home over the mock ports. No real crash report of DevHub was read in this session.
- `ToasterTests.textHidesAfterADelay` can fail when the Mac is under heavy load, because it waits for a real delay. A second run passes.
- Window mode: the global shortcut and a real click on the Dock icon were not tried; `open` on the running app (the same reopen event) was.
- The simulator QA panel, the line comment box and the job log were checked by tests and by running the commands by hand, not by clicks in the panel.
- The project list keeps projects whose folder no longer exists (for example old test folders). They show in the menu, the palette and the right-click menu.

- Settings with no project: the Settings tab also shows "No project yet" until a project is added. Adding a project works from that screen and from the header menu.
- `xcrun simctl boot` on a booted simulator shows a red row in the Output panel (exit code 149). The run goes on: the repository accepts that code, but the command log does not know it.
- Auto-merge on GitHub was not seen working: the test repository is private on a free plan, which has no branch protection and no auto-merge. The action stays hidden there (`autoMergeAllowed` is false).
- GitLab: approve, unapprove, auto-merge and pipelines were not checked on a real host. Create, draft and ready, threads, merge, labels and diffs were (`GlabIntegrationTests` on a private test project of the owner).
- Push on a branch with an upstream runs plain `git push`, so git uses its own upstream and `git.remote` does not apply there.
- macOS notifications were checked by tests only: the permission prompt was not accepted in this session, so no banner was seen.
- The context menus of rows were checked by tests only: a headless snapshot does not open a menu.
- With `xcode.bundleIDs` per scheme, the identity panel reads the app of the effective scheme until the first launch from DevHub on that simulator (decision 30).
- Launch & Attach in a simulator row needs `launch.identity`: without it DevHub does not read whether the app is installed.
- The first read of the AI tab takes several seconds when `~/.claude/projects` and `~/.copilot/session-state` hold about 1 GB; later reads use the cache.
- The messaging panel and Resume in the AI tab were checked by tests only: a headless snapshot cannot open the panel or click a button.
- The global shortcut was checked only with headless snapshots, not with a real key press. The right-click menu of the status item was checked with a synthetic right click (ADR 005 W2).
- Esc clears the search field but does not close the panel. A click outside the panel closes it.
- The "Build" button, the resizable Output panel, the "New" AI session menu and the own request reports were checked by tests and headless snapshots, not by clicks.
- A click on a macOS notification (the `didReceive` delegate call) was checked by tests of the codec only: no real notification was clicked in this session.
