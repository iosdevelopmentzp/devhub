## Decisions

Numbered. What, then why. A later session must not undo these without a new numbered entry that explains the change.

1. The remote `origin` is a public GitHub repository, and `main` is pushed after green commits. Never force-push. Why: the owner decided so on 2026-10-30, to use the app on another Mac. The code was never pushed before that date. Everything pushed is public, so the anonymity check runs before every push. A separate playground repository tests the pull request features.
2. Own `NSStatusItem` and `NSPanel`, not `MenuBarExtra`. No sandbox, ad-hoc signing, `LSUIElement`. Why: shell commands need it, and the panel needs its own position, size and close rules. Changed by ADR 005 (2026-10-27): a second mode, "Normal window" (Settings → General → Window), gives one main window with a Dock icon and a main menu. The panel stays the default, so `LSUIElement` stays `YES` and window mode sets the activation policy to `regular` at start. `AppContainer` is the app delegate, for the Dock click.
3. Config over code: no project name, path, bundle ID, host or branch name in Swift. `Scripts/check-anonymous.sh` enforces the names; `.claude/rules/anonymity.md` lists the sample vocabulary.
4. The owner's own words live in `~/.devhub/anonymity-denylist.txt`, outside the repository. Why: the list itself would name the projects.
5. The package architecture of the main DevHub is the base: modules `Domain`, `Data`, `Mocks`, `UI`, `Presentation`, `Composition`, `TestSupport`, Swift 6, Swift Testing with spies. `docs/ARCHITECTURE.md` is the contract.
6. Common branch names (`main`, `master`, `develop`, `dev`) are not project names and may appear in tests and defaults. The remote comes from `git.remote` (`GitSettingsPolicy.defaultRemote` is `origin`), and every git command, `BranchName` and policy takes the remote name as a parameter.
7. The first launch has no project. `ProjectSession.selectedProject` falls back to `Project.none` and `RootView` shows `NoProjectState` instead of a tab. Why: the main app had a fixed default project, and a generic app cannot know one.
8. The Network tab lists only the exchanges of the DevHub mock server. Why: the session log was the log format of one app. `NetworkStore` keeps selection, filter, pause and clear over the server exchanges.
9. Debug launch switches live in `DevHubComposition/Debug/DebugLaunch.swift` and are compiled in Debug builds only. Today: `DEVHUB_PROJECT`, `DEVHUB_OPEN_PANEL`, `DEVHUB_TAB`, `DEVHUB_SNAPSHOT`, `DEVHUB_SNAPSHOT_DELAY`, `DEVHUB_RUN_ACTION` (comma-separated action ids, run with default inputs), `DEVHUB_REQUEST_ACTION` (one id, opens its prompt), `DEVHUB_SHOW_OUTPUT`, `DEVHUB_GIT_OPS` (comma-separated steps such as `fetch,stage:a.txt,commit:Message,push,wt-create:feature/x,switch:topic,delete-branch:topic`; each step waits until the stores are idle; the list is in `PresentationAssembly+DebugGitOps.swift`). `DEVHUB_PROJECT`, `DEVHUB_TAB` and `DEVHUB_SHOW_OUTPUT` change saved preferences. Later switches: `DEVHUB_WINDOW_MODE` (`panel` or `window`, saved), `DEVHUB_PULL_REQUEST` (a number: opens that request in the Pull Requests tab), `DEVHUB_BUILD_RUN` (with `DEVHUB_BUILD_PROFILE`, `DEVHUB_BUILD_BRANCH`, `DEVHUB_LAUNCH_ID`), `DEVHUB_MOCK`, `DEVHUB_LOG_STREAMS`, `DEVHUB_PALETTE`.
10. Snapshot trap: SwiftUI does not redraw a panel that is covered by other windows, and `cacheDisplay` does not draw some controls (a prominent button looks empty). Check results on the command line as well as in the picture.
11. The scripts stop only the build of this repository, by its executable path. Why: another app with the same name (`DevHub`) can run on the same machine.
12. The app keeps the bundle ID `devteams.DevHub` of the first generic app, so it reads and writes the same preferences domain.
13. "Copy for Slack" is "Copy Link with Title" (`RequestLinkText`): the reference, the title and the link.
14. `waitUntil` waits 10 s by default, not 2 s. Why: right after a build, about 25 store tests timed out on the busy main actor while the same tests passed alone. The wait is the main-actor queue of a parallel run, not CPU load (decision 47).
15. The `.devhub/` config models are `Codable` Domain types (`Models/Config/`), the one exception to "no `Decodable` Domain model" (`docs/ARCHITECTURE.md` section 5). `ExampleConfig.files` is generated from `docs/examples/devhub/` by `Scripts/generate-example-config.sh`; run it after every change there.
16. After a change to an enum in a lower module (for example a new `Tint` case), remove `Packages/DevHubKit/.build` before `Scripts/test.sh`. Why: the incremental test build once kept old object files, and the tests read wrong enum values.
17. A config action in a row placement shows its inputs and confirmation under that row. The screen draws the prompt (`ConfigActionsStore.pending(in:)` with the slot `<placement>:<row id>`), the row gets only `configActions` in its model and an `onConfigAction` closure. Why: a row reads no store but `Toaster` and `AppActions`.
18. A remote whose host name contains neither `github` nor `gitlab` counts as GitLab unless `git.host.kind` says `github`. Why: a self-hosted GitLab on a company domain is the common case; GitHub Enterprise users set the kind once. The ADR idea to ask `gh auth status` was dropped: it would make the choice depend on the machine.
19. The code host types use pull request words: `PullRequestSummary`, `CodeHostRepository`, `PullRequestsStore`, `ReviewThread`, `MergeReadiness`, `CheckStatus`, the tab id `pullRequests`. The fields keep their names (`iid`, `pipeline`, `detailedStatus`), and the GitLab GraphQL strings keep the GitLab names (`MergeRequestState`, `mergeRequests`). Why: a field rename touches every mapper and test for no change in behaviour, and the GraphQL names belong to GitLab.
20. `.gitignore` ignores only the top-level `/build/` folder. Why: on the case-insensitive macOS file system `build/` also matched every `Build/` source folder, and the Build feature was missing from the commits.
21. UI words for the code host come from `CodeHostWords` (`Shared/`): "Pull Requests" and `#12` for GitHub, "Merge Requests" and `!12` for GitLab, "checks" or "pipeline". Mappers take `words:`; views and rows read `@Environment(\.codeHostWords)`, which `CodeHostRemote` sets after the first read of the remote. Before that the words are neutral ("Pull Requests", "Open in Browser"). Why: one place for the vocabulary, and rows need no new store.
22. Actions that a host or a repository does not allow are hidden, not shown with an error: `PullRequestPermissions.canRevokeApproval` (GitHub: write access) and `canSetAutoMerge` (GitHub: write access and `autoMergeAllowed` on the repository).
23. A `kind: command` project runs `build.command`, then `run.command`, in the checkout of the run bar, with the action variables (`DEVHUB_SIMULATOR_UDID`, `DEVHUB_BRANCH`, …). Both commands may print `@devhub {"app": "<path>"}`; a relative path is read from the checkout. A script file without the executable bit runs through `/bin/zsh`. Run & Attach stays off for these projects. Why: the app path is known only after the build, and a fresh clone often loses the executable bit.
24. Deep link schemes come from `CFBundleURLTypes` in the `Info.plist` of the app installed on the simulator, not from a `simulators.deepLinks` config key (ADR 001 section 7.5). Why: the app already declares its schemes, and a new key would change the config schema.
25. The AI tab does not check that `copilot` or `claude` is installed before Resume. Why: Resume runs in the terminal with the PATH of the user; the app's own PATH misses folders such as `~/.local/bin`, so a check from the app would hide working sessions. Settings → Doctor shows missing tools.
26. The Copilot token comes from `gh auth token` first and from the `copilot-cli` keychain item second. The keychain read stops after 10 s and is not tried again until the app restarts. Why: macOS can ask the user to allow `/usr/bin/security` to read that item; a background refresh every 5 minutes must not keep that dialog open or show it again and again.
27. The M6 config keys follow ADR 001 Appendix A, approved by the owner on 2026-10-18: `launch.identity.*`, `launch.profiles[].storage`, `upstream` and `production`, `network.baseURLVariable` and `network.mocksFolder`, and the `state` directive of the status script.
28. A launch identity is a plan, not stored state: `LaunchPlan` joins the profile, `launch.identity` and the chosen ID, and every launch (Build & Run, Launch, Apply & Relaunch) goes through `simulators.launch` with its environment and arguments. The result is a `LaunchRecord` (bundle ID, profile, ID, mock server URL) that `IdentityStore` saves per simulator under `simulators.launchSettings`. The old key `simulators.identity` is not migrated. Why: the old settings held an environment name and a hard-coded device ID format that no longer exist; a reset costs one choice per simulator.
29. The clean install rule (`CleanInstallPolicy`): with a chosen ID, reinstall when the actual ID (the `state` report, else the last ID DevHub set) differs. With no chosen ID, reinstall only when the actual ID is one that DevHub set or saved. With a chosen ID and no known actual ID (no `state` report and no earlier launch from DevHub), the first launch reinstalls once. Why: the app's own ID must not cause a reinstall on every Build & Run; that would lose the session each time.
30. The bundle ID of the identity panel and the mock server is the one of the last launch on that simulator when the project config knows it, else the effective bundle ID of the project. Why: `IdentityStore` sits below `BuildStore` and cannot read the run bar scheme; the last launch records what Build & Run really installed.
31. A custom tab has no store of its own: `CustomTabMapper` turns the tab config into sections, and the rows run through `ConfigActionsStore` like the scripts on Home. A source script is the header script action `script:<file name>`, so its run, result and last run time are shared with Home. Why: one place runs config scripts and keeps their results; a second store would copy that state.
32. Notifications for Build & Run and review requests go out only while the panel and the pinned window are both closed (`Notifier.postWhenClosed`). A `notify` directive of a script posts always, because the script asked for it. The permission is asked only from Settings → Notifications, never at app start. Why: an open panel already shows the result, and a permission dialog at start interrupts the user before DevHub did anything useful.
33. `PathToolLocator` looks in `/opt/homebrew/bin`, `/usr/local/bin` and `~/.local/bin` before the `PATH` of the app. Why: an app started from Finder or at login gets a short `PATH` without these folders, and Doctor would call installed tools "missing".
34. A GraphQL response with an `errors` array counts as failed in the Network tab, even with HTTP status 200. A mock rule matches a GraphQL operation by `operationName` with `*` as a wildcard; a batch matches when one of its operations matches. Why: GraphQL servers answer 200 for most errors, so the status code alone hides them.
35. The first custom tab gets ⌘9, after the eight built-in tabs. Tabs after the ninth have no shortcut. Why: ⌘1 to ⌘8 must stay the same in every project.
36. The mock server of a simulator first tries a stable port from a hash of the simulator UDID (`MockServerPortPolicy`, 49152 to 59151) and takes any free port when that one is busy. Why: the app keeps the same base URL across DevHub restarts, so a relaunch is needed less often.
37. Two window modes: "Menu bar panel" (the default) and "Normal window" (ADR 005). `LSUIElement` stays `YES`; window mode sets the activation policy to `regular` at start, and `AppContainer` is the app delegate for the Dock click. Why: the main DevHub moved to a window app, but a generic app should keep the menu bar panel for users who want it.
38. `PullRequestPermissions.canRequestChanges` is true only on GitHub for a request by someone else. GitLab has no "request changes" review in `glab`, so the button is hidden there, not shown with an error (decision 22).
39. Simulator QA settings go through the typed `SimulatorSettingsRepository` port, and the language change waits for a reboot instead of rebooting the simulator. Why: a reboot closes the app under test without asking.
40. A job log in pull request details is cut to its last 200 lines in Data (`JobLogTail`), with timestamps, colour codes and tokens removed. Why: GitHub and GitLab logs can be many megabytes, and the end of the log holds the failure.
41. `Scripts/install.sh` installs to `/Applications/DevHub Generic.app`, not `/Applications/DevHub.app`. Why: the main DevHub lives at `/Applications/DevHub.app` and updates itself from its own repository; both apps must run on one Mac. The bundle IDs differ, so settings stay apart. Both apps can use the same global shortcut only if one of them changes it in Settings.
42. The files that the pull request details hide come from `git.pullRequests.hiddenFiles` with a built-in default (`GitSettingsPolicy.defaultHiddenFiles`: tests, Xcode project files, lock files), matched by `fnmatch` against the full path and the file name (`HiddenFilePolicy`). The hidden state is per request and lives in memory (`PullRequestDetailStore.shownHiddenFiles`). Why: the owner wants to review the main code first; a default makes it work without config, and a project can set `[]` to hide nothing. GitLab has no `approvalsRequired` or `approvalState` field on the owner's server, so the review block names people and never counts approvals.
43. Changes of your own open requests (approval, request for changes, failed checks, new comments, merged, closed) come from a comparison of two reads of the open list (`OwnRequestChangePolicy` in `OpenPullRequestsStore`), not from a new poll. A request that left the list gets one `status` read of its branch to tell a merge from a close. A refresh caused by your own action (`.pullRequestsChanged`) updates the baseline without a report. Why: the open list is read every 5 minutes in any case, and a report after your own comment or approval would name your own action.
44. "Build" (⌘B) is the Build & Run pipeline with `BuildRequest.launchesApp == false`: it stops after "Locate the app", and a `kind: command` project runs `build.command` only. `builtin.build` is not in the default Home grid (like `builtin.pullRequests`). Why: one pipeline, one store, one log; the grid stays at eight tiles.

45. Notification kinds are stored as the muted set (`AppSettings.mutedNotifications`), so a new kind is on by default and an old settings file keeps every kind on. The events of the app (`ActivityLog`) carry a kind and a place (`ActivityTarget`) and are saved for 30 days (`ActivityRetentionPolicy`, 500 at most) under `app.recentEvents`; the same event feeds the macOS notification, the Notifications screen and Recent on Home. Why: one list to look at, one place to mute a kind, and a click that leads somewhere.

46. CI runs on a GitHub-hosted `macos-26` runner (`.github/workflows/ci.yml`): layer check, anonymity check with the built-in patterns only, Debug build, smoke check, every test in a serial run. Why: two process hangs in `ShellRunner` and a test race were found by hand in parallel sessions; a run on a clean machine catches them before a push lands on `main`. The denylist is private, so CI cannot check the owner words.
47. CI runs the tests serially (`Scripts/test.sh --no-parallel`). Why: `swift test` queues every test at once, and in a parallel run every hop to the main actor waits for the queued main-actor tests: about 3 s on 14 cores, about 10 s on the 3-core runner, which is the `waitUntil` timeout, so the store tests timed out in every second CI run. A serial run has no queue. A local run stays parallel: 3 s is far from the timeout and the run takes 4 s instead of 17 s.
48. CircleCI through one Domain port (`CIRepository`) over the `circleci` CLI, on only when `CIPolicy.provider` finds `ci.kind: "circleci"` or `.circleci/config.yml` in the main checkout. Why: the GitHub checks stay the source of truth for the state (the link of a check carries the workflow UUID, `CIWorkflowLink`), and the tool adds the jobs, the logs, re-run, cancel, approve and the failed tests with the flaky label from CircleCI Insights. DevHub never calls the CircleCI web API itself and never holds the token (ADR 006). The fixtures follow the CLI reference; a live check is still open.

## Known gaps

- CircleCI: the parsers follow the CLI reference of October 2026. A live project with the OAuth integration showed that a commit status links to `app.circleci.com/workflow/<uuid>/job/<uuid>` (read since the fix) and that `circleci workflow get` answers such a workflow with its jobs. The field names of the parsers against a live answer and the approve command are still open questions in ADR 006.
- Window mode: the global shortcut and a real click on the Dock icon were not tried; `open` on the running app (the same reopen event) was.
- The simulator QA panel, the line comment box and the job log were checked by tests and by running the commands by hand, not by clicks in the panel.
- The project list keeps projects whose folder no longer exists (for example old test folders). They show in the menu, the palette and the right-click menu.

- Settings with no project: the Settings tab also shows "No project yet" until a project is added. Adding a project works from that screen and from the header menu.
- `xcrun simctl boot` on a booted simulator shows a red row in the Output panel (exit code 149). The run goes on: the repository accepts that code, but the command log does not know it.
- Auto-merge on GitHub was not seen working: the test repository is private on a free plan, which has no branch protection and no auto-merge. The action stays hidden there (`autoMergeAllowed` is false).
- GitLab: approve, unapprove, auto-merge and pipelines were not checked on a real host. Create, draft and ready, threads, merge, labels and diffs were (`GlabIntegrationTests` on a private test project of the owner).
- Push on a branch with an upstream runs plain `git push`, so git uses its own upstream and `git.remote` does not apply there.
- macOS notifications were checked by tests only: the permission prompt was not accepted in this session, so no banner was seen.
- The context menus of rows were checked by tests only: a headless snapshot does not open a menu.
- With `xcode.bundleIDs` per scheme, the identity panel reads the app of the effective scheme until the first launch from DevHub on that simulator (decision 30).
- Launch & Attach in a simulator row needs `launch.identity`: without it DevHub does not read whether the app is installed.
- The first read of the AI tab takes several seconds when `~/.claude/projects` and `~/.copilot/session-state` hold about 1 GB; later reads use the cache.
- The messaging panel and Resume in the AI tab were checked by tests only: a headless snapshot cannot open the panel or click a button.
- The global shortcut was checked only with headless snapshots, not with a real key press. The right-click menu of the status item was checked with a synthetic right click (ADR 005 W2).
- Esc clears the search field but does not close the panel. A click outside the panel closes it.
- The "Build" button, the resizable Output panel, the "New" AI session menu and the own request reports were checked by tests and headless snapshots, not by clicks.
- A click on a macOS notification (the `didReceive` delegate call) was checked by tests of the codec only: no real notification was clicked in this session.
